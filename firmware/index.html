Firmware

The firmware part is the hard part.

Most of a cyber-resilience file can be written by a lawyer. The parts that get rejected are the ones that need someone to read the boot chain: is the update actually signed, does the device refuse an old image, can a key be extracted from flash, and can you prove it three years later when a component you shipped has a CVE.

Describe the product What we deliver

Why this is where products fail

The reporting duty under Article 14 has applied since 11 September 2026: an actively exploited vulnerability has to reach ENISA and the national CSIRT within 24 hours, with a notification at 72 hours and a final report at 14 days. That clock does not start in a policy document — it starts with someone being able to answer, within an hour, whether a given CVE affects a given release. If the answer requires rebuilding an image to find out, the deadline is already gone.

The same gap shows up earlier, in the radio equipment route: EN 18031 has applied since 1 August 2025, and its clauses on secure updates, access control, key storage and network monitoring are firmware clauses. Products that claim them without a signed update path and a protected key store do not survive a technical review.

What we deliver

Signed update chain

engineering

Key hierarchy, image signing, on-device verification, rollback and anti-rollback protection, staged rollout, recovery path. Implemented in the build, not described in a slide.

Secure boot

engineering

Root of trust selection for the silicon you already ship: boot ROM, fuse-based verification, TPM or secure element, measured boot where it is available. Includes the provisioning procedure and what happens when a key is lost.

Firmware review

assessment

Boot chain, update path, credential and key storage, debug and recovery interfaces, factory and service modes, update server authentication. Written up as findings an assessor can follow, with the reproduction each one needs.

SBOM and vulnerability handling

process

SBOM generated at build time and stored with the release, dependency monitoring, triage that separates not-affected from exploitable, a CVD policy with a working intake channel, and a rehearsed 24-hour reporting path.

Assessment evidence

documentation

The technical sections of the file: architecture and data flow, security requirements mapping, test records, and a traceable link from each requirement to the artefact that satisfies it. Built to be read by someone who will test the claim.

Retrofit on shipped products

engineering

For hardware already in the field. Where the boot ROM allows it, a signed update path can be added without a board revision; where it does not, we say so early and price the alternative honestly.

How an engagement runs

Day 1
Scope. One call, then a written scope: product, silicon, whether the update path already exists, and which claims in the file need evidence.
Days 2–3
Fixed price. A priced list, not an estimate. Nothing starts until the scope is agreed in writing.
Weeks 1–4
Work. Review, then implementation, then re-test. Findings are delivered as they are confirmed, not saved for a final presentation.
Handover
Evidence. Documents, test records and the signing or provisioning procedure, in a form your assessor can follow without us in the room.
